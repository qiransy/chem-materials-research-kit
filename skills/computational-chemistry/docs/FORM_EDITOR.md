# 结构化方案编辑器

默认最终审查只在阶段一渐进式信息采集完成后生成，固定使用 `.review/review.html`，修改时覆盖同一文件。页面应使用表单、下拉框、开关、复选框和数字输入框，不要求无基础用户编辑大段 JSON。

下述更完整的编辑器由仓库现有阶段一资源实现，供显式初始化的高级项目使用。其 JSON 视图是专家可选模式，不是默认入口。

方案编辑页面面向没有 JSON 和编程基础的科研用户。JSON 仍是系统内部的数据交换和持久化格式，但普通用户默认通过结构化表单编辑研究方案。

## 编辑模式

页面提供两个模式：

- **表单模式**：默认入口，使用自然语言字段、卡片、选择器、数字框和依赖控件。
- **高级 JSON 模式**：供熟悉 Schema 和字段结构的技术用户使用。

两个模式操作同一份内存数据。任何模式保存前都必须完成语法、Schema 和数据一致性校验，不得维护两份可能互相偏离的数据。

## 页面结构

推荐顺序：

```text
项目状态与版本
方案完整度与待确认事项
研究目标
科学问题
计算任务
软件与模块
方法与参数
依赖与执行顺序
替代方案
受保护字段修改记录
自然语言修改摘要
底部操作栏
```

## 系统字段

以下字段由系统生成或维护，普通用户只读：

- `schema_version`
- `project_id`
- `stage`
- `status`
- `version`
- `request_id`
- `content_hash`
- `created_at`
- `updated_at`
- `confirmed_at`
- 科学问题内部 ID
- 任务内部 ID
- 依赖引用 ID

普通表单不得允许用户直接删除或覆盖这些字段。高级 JSON 模式也应保护会破坏状态机、版本链或审批校验的关键字段。

## 研究目标

研究目标区域使用自然语言标题，不以英文键名作为主要界面文本。至少包括：

- 研究对象
- 比较对象
- 已知实验现象
- 核心科学问题
- 预期获得的结论
- 研究边界或不包含内容

“已知实验现象”使用选择式输入：未提供、已有、本任务不涉及。只有选择“已有”时才显示详细文本框。

“预期获得的结论”应提醒用户填写希望通过计算回答的问题，不得把尚未计算的内容写成确定事实。

## 科学问题卡片

`scientific_questions` 使用卡片编辑，每张卡片包括：

- 科学问题
- 所需证据
- 前置依赖
- 支持的结论
- 不支持的结论
- 备注与限制

用户可以新增、复制、删除、上移和下移。内部 ID 由系统自动生成，普通用户不需要维护 `SQ01`、`SQ02` 等编号。

依赖关系通过下拉框或复选框选择其他问题，保存时自动转换为内部 ID。删除被依赖的问题前，系统必须显示受影响对象并要求重新设置依赖，不能生成悬空引用。

## 计算任务卡片

每个任务至少包括：

- 任务名称和目的
- 软件与模块
- 研究体系或模型版本
- 直接输入参数
- 直接输出参数
- 输出参数代表的性质
- 可支持的结论
- 不可支持的结论
- 前置任务
- 与其他结果的佐证关系
- 优先级
- 预计计算成本
- 完成条件

第一阶段只制定任务目标和方案，不生成正式输入文件，也不运行计算。

## 软件、方法与参数

软件字段应使用可搜索选择器并显示软件名称、版本和模块。参数根据数据类型使用：

- 数值输入框
- 单位选择器
- 枚举下拉框
- 布尔开关
- 文本说明
- 可编辑表格

不得把整个参数对象作为 JSON 文本交给普通用户。软件之间的关键字和方法不得默认视为一一等价。

## 受保护字段与 manual_overrides

普通用户不直接编辑 `manual_overrides`。修改受保护字段时，系统弹出对话框并要求填写：

- 字段名称与路径
- 当前值
- 新值
- 修改理由
- 对任务、证据链、工作量、结果范围或风险的影响

确认后自动生成覆盖记录，至少包括：

```json
{
  "field_path": "research_goal.core_question",
  "old_value": "...",
  "new_value": "...",
  "reason": "...",
  "modified_at": "ISO-8601 时间"
}
```

修改理由不能为空。人工覆盖状态应在表单中可见，并允许查看原值和理由。

## 输入辅助

主要字段旁可以提供：

- 解释此字段
- 生成填写建议
- 查看示例
- 恢复原建议

AI 建议只能写入可编辑输入框，不能自动保存、提交或批准。示例应同时说明合理写法和常见错误。

## 实时校验

编辑过程中应定位到具体字段，至少检查：

- 必填字段缺失
- 科学问题过于宽泛
- 研究对象缺少结构来源
- 软件、方法和参数不兼容
- 单位或参数格式错误
- 依赖对象不存在
- 循环依赖
- 重复问题或任务
- 任务缺少输入、输出或证据用途
- 目标结论使用未经支持的绝对表述
- 受保护字段修改但缺少理由
- 未知扩展字段在模式切换中丢失

页面顶部显示方案完整度、待确认事项、阻塞提交的问题和一般提醒。完整度不能只按非空字段数量计算。

## 操作区

### 保存草稿

保存当前编辑内容，不进入审批，不覆盖已批准版本。

### 检查方案

执行完整 Schema、字段、依赖、软件兼容性、参数格式和人工覆盖检查。

### 查看修改摘要

默认生成自然语言差异，包括研究目标、科学问题、任务、软件、方法、参数、依赖、工作量、证据链、结果范围和风险变化。技术用户可以进一步查看 JSON Diff。

### 提交审批

只有阻塞性检查通过后才能提交。提交前显示用户即将批准的完整方案摘要，并生成新的 `request_id` 和 `content_hash`。

## 高级 JSON 模式

高级编辑器至少支持：

- 语法高亮
- 自动格式化
- 括号匹配
- 撤销和重做
- 错误行与列定位
- 字段路径提示
- Schema 校验
- 未知字段保留
- 恢复最近有效版本

语法错误应显示具体行号和原因。Schema 错误应显示字段路径。无效 JSON 不得覆盖当前有效表单数据。

## 双向同步规则

模式切换和保存必须保证：

- 已知字段正确映射
- 未知字段不丢失
- 内部 ID 不无故重建
- 数组顺序不改变
- 依赖引用不丢失
- `manual_overrides` 不丢失
- 数值、布尔值和空值类型不漂移
- 系统字段不被普通表单覆盖

表单、版本文件和审批请求必须来源于同一份已经校验的数据。

## 可访问性与普通用户体验

界面应使用明确的自然语言、清晰分区和可折叠卡片。避免密集技术表格、只有字段路径的错误信息和大量缩写。按钮名称使用“保存草稿”“检查方案”“提交审批”等任务语言，而不是内部函数名。

## 验收要求

必须测试：

- 现有方案 JSON 正确加载为表单
- 普通字段修改与草稿保存
- 科学问题和任务新增、删除、排序与依赖
- 删除被依赖对象时的保护
- 受保护字段自动生成覆盖记录
- 无理由时阻止提交
- 表单与 JSON 双向同步
- 无效 JSON 不覆盖有效表单
- 未知字段保留
- 旧版本数据兼容
- 修改摘要为自然语言
- 提交审批仍绑定当前请求、阶段和哈希

任何数据丢失、类型漂移、依赖损坏或审批绕过都应判定为验收失败。
